## 비교 조건

본문 900자/중복 150자, 모든 청크에 식별·출처·시각 헤더. Embedding `text-embedding-3-small`, FAISS, Top-K 3. 생성 모델 `gpt-4o-mini`, temperature 0. Hybrid는 BM25 + vector 후보를 RRF(상수 60)로 결합한다. 데이터와 질문은 첫 Baseline 전에 고정했다.

검색 비교는 같은 데이터·질문·Prompt를 사용한다. 생성 개선은 최초 Baseline의 검색 문맥을 그대로 재사용한다. 최종 실험은 Hybrid와 프롬프트를 동시에 바꾸지 않았으므로 어느 변경의 효과인지 구별할 수 있다.

## 실패 원인과 개선 선택

1. **검색:** Baseline은 정답을 찾았지만 동명 타 단체 물품이 함께 검색됐다. Hybrid는 다른 단체 청크를 11개에서 3개로 줄였다. Hit Rate와 주요 답변 정확도 향상은 확인되지 않았다. 따라서 Hybrid는 후보로 유지하며 운영 품질 향상을 주장하지 않는다.
2. **생성:** 문서가 기간 원값 6만 제공했는데 Baseline/Hybrid가 모두 “6일”을 답했다. 시스템 지시와 사용자 질문·참고 데이터를 분리하고 기간 단위 규칙/예시를 추가했다. 같은 검색 근거에서 기간 오류는 없어졌다.
3. **회귀:** v2는 목록 수집 실패를 “물품 없음”으로 단정했다. 실패한 단체의 전체 이름이 질문에 있고, 검색된 단체 목록이 수집 미완료이면 모델 대신 확인 불가와 출처/시각을 반환하는 처리를 추가했다. 관계없는 단체의 실패가 검색돼도 차단하지 않는 테스트를 추가했다.
4. **최종 검증:** v2 답변 10개를 재사용하고 Q9만 코드 처리로 대체했다. 추가 LLM 호출은 0회다. 최종 결과를 모델 전체 재실행 성능으로 오해하지 않아야 한다. 실패 처리의 적용 범위는 검색된 목록과 질문의 단체 전체 이름 일치이며 별칭/일부 이름에 대한 보장은 없다.

## 호출 및 검증

mock 생성은 외부 조회 0회. 모델 실험은 Baseline 생성 10회 + 비교 생성 20회 + v2 생성 10회 = 40회. 문서 임베딩 2번(각 29개), 질문 임베딩 20회. 토큰 실사용량과 금액은 기록하지 않았으므로 비용을 추정해 기재하지 않는다.

로컬 테스트 5개 통과: 커서 타입/반복, 페이지네이션/중복/상세 실패, 목록 실패, mock 표시/정답 근거, 실패한 대상 단체만 제한하는 처리. 문법 검사와 diff 공백 검사도 수행한다.

## 앞선 테스트 서버 실험 (주 평가와 분리)

운영 전 EC2 테스트 서버에서 리트리버 단체 물품 3종, 문서 4개를 수집했다. 조회 5회, 오류 0회. 10개 질문 중 답 있는 8개는 Baseline/Hybrid Hit@3 8/8. Hybrid는 3문항에서 정답 문서를 2순위로 밀었다. 기간 원값 3을 “3일”로 단정하는 생성 오류가 있었다. 초기 프롬프트 수정은 소속/미래 수량 회귀가 발생해 채택하지 않았다. 사용자 지시에 따라 그 서버의 추가 실험을 중단하고 mock 실험으로 전환했다. 키는 `.env`보다 기존 환경변수가 우선하던 문제를 수정한 뒤 정상 인증 확인했다.

## 운영 최종 검증 계획

운영 서버의 API 경로·응답 구조·인증 여부는 아직 확인하지 않았다. 최종 검증 때 수집할 실제 키워드를 정하고 소규모 조회로 확인한다. `--base-url https://www.retrivr.kr`로 명시적으로 지정하며 새로운 production 스냅샷과 질문/결과 파일을 사용한다. mock 데이터와 섞지 않고 호출 규모를 먼저 확인한다. 재수집 시에는 실제 근거로 운영 질문을 따로 고정하며 mock 수치를 운영 성능으로 재사용하지 않는다.
